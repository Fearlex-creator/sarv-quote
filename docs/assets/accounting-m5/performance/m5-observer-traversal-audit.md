# M5 observer traversal audit

Read-only audit,2026-10-08UTC; candidate5 functional qualification only. The M5 observer and its historical timing endpoints are unchanged. No C2 measured epoch is rerun or corrected. Breadth-first traversal overhead is a **hypothesis**, not an isolated cause or a budget waiver.

Normal timed lookups use `scripts/accounting-performance.py:85` `first_accessible`: a `deque`, at most8,000 visited nodes, early exit at the first matching node. Each visited node clears AT-SPI cache, evaluates the predicate and enumerates children. `Access.children` calls child-count and then one child-accessor per child. Name, role, text, state, rectangle and focus checks add further C/AT-SPI calls. Cross-process delivery, GTK accessibility work and client scheduling contribute to wall-clock duration. This is not a pure-Python list-front-removal problem: the normal helper already uses a deque. `qa_access.py:75` `tree` does use `list.pop(0)` and exhaustively collects names/roles, but M5 invokes it for retained focus-failure diagnostics; that does not explain successful search/page timings by itself.

`observe` sleeps5ms **after** each predicate invocation; a predicate containing multiple remote traversals can take substantially longer than5ms. Actual observation cadence is predicate duration plus sleep and scheduling, not a guaranteed5ms sample clock. Initial control discovery/search reveal/focus are excluded before each timed dispatch where the original method specifies them. Current-result discovery, rendering/focus checks and result navigation after dispatch remain included. Synchronous database equality and screenshots are outside read-only search/page sample timers, although they affect subsequent shared scheduling and caches.

The scoped root limits unrelated workspace traversal, but hidden descendants may still exist in AT-SPI. A node-count limit bounds the number of visits, not a wall-clock deadline for a slow individual call. `qa_access.py` configures AT-SPI timeouts1000/1500ms. The pilot contains no per-call/traversal duration, visited-node count or remote IPC count, so this audit cannot quantify how much of any latency came from observation versus GTK rendering, scrolling/focus, debounce or shared contention. Diagnostic process-shutdown cache warnings remain raw; their mere presence does not establish an in-sample timeout.

Potential future instrumentation would record visited-node count, predicate calls, cache/name/role/child/state/focus calls and traversal wall time under stable observer/source hashes. It would retain the same exact query/count/current-ID, visible/sensitive allocated action and actual focus acceptance conditions. Caching a currently installed control or scoping discovery more narrowly must still reject stale results after query, page or generation changes; direct callback dispatch or a stale retained node cannot replace native readiness. Any instrumentation/optimization is a new declared observer version with fresh bounded qualification and a separately attributed final epoch. Reduced observer overhead changes the observed latency even if the user-facing acceptance condition remains the same; it does not establish a controlled causal application-speed comparison with C2.

No traversal optimization, diagnostic timing subtraction, relaxed200/150ms budget or replacement endpoint was implemented for candidate5 qualification. Candidate5 n1 startup/n2 query timings under concurrent authorized diagnostics are not accepted final percentiles.
