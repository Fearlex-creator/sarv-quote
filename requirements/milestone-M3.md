## Visible version-one defaults

Review `core-policy-v1` before creating fresh books: accrual/perpetual combined goods delivery recognition, canonical integer IRR, quantity thousandths, positive half-up whole-rial rounding, moving weighted average per company/item/warehouse, original-allocation cumulative/final-residual returns, no negative stock, no stock backdating and tax disabled. Display the effective civil date and company timezone (`Asia/Tehran` or `UTC` as supported); persist canonical ISO civil dates independently of recorded-at UTC timestamps. The guide's proposed settings become explicit engineering choices under the user's delegation; they are not tax/accounting certification.

The proposed chart covers 21 stable roles across assets, liabilities, equity, revenue and expense. Codes/Persian names are editable labels; stable IDs and validated mappings carry meaning. Ten mapped balance-sheet roles have opening detail registers and require explicit ledger opening balances, **including zero advance controls**. COGS and inventory-loss accounts remain protected movement roles with mandatory zero opening; their protection does not add fabricated opening registers. Preview therefore checks **twelve controlled accounts: ten registers plus two explicit zero movement roles**. Setup and opening snapshots are immutable after posting; the opening retains its frozen setup/policy/mappings and full-command digest. M3's fresh-company contract is narrower than the proposal's future additive existing-book design: configure/reconfigure only when allowed by validated fresh-book state, never silently remap referenced balances or post a second opening. Invalid/missing/duplicate/cross-company/archived/nonpostable/wrong-class/wrong-normal-side mapping rejects before mutation.

Selecting an MWA or original-cost-return policy does not ship stock movements or returns. The next connected sales/purchases/inventory/returns milestone must independently prove those calculations and event lifecycles. A disabled tax profile asserts neither exemption nor compliance; legacy quotation snapshots remain unchanged.

## Posting, retry and immutable-history acceptance

The command boundary owns the entire detailed opening. Preview is read-only; cancel/invalid input leaves no financial effects. Commit validates policy/setup/company/fiscal boundary, source/reason/actor, IDs/provenance, balanced ledger, all twelve controlled-account checks and GRNI subset before atomically installing the opening effect, frozen setup/policy/mappings, full-command digest, immutable detail registers and activity. Imported data additionally freezes file checksum and source row IDs/kinds/original values; a financially equivalent normalized import must not silently replace different original provenance on retry. The canonical economic event is one company initialization (`core.opening.v1`); changing a caller source ID or retry key cannot create another opening.

Financial journals still require **at least two meaningful financial lines** under ACC-02. An entirely zero monetary opening records `OpeningEffect::ZeroBalanceInitialization` and one `CoreOpeningInitialized` audit marker, **no Journal and no normal PostRequestRecord**. Its stable initialization ID is distinct from a financial journal and reserved across all entity IDs. Separate `zero_requests` retain full-command digest/company/marker identity and enforce request-key collisions against ordinary financial requests in both directions. Marker replay/restore must validate the frozen policy/setup, source/provenance, explicit control zeros and complete command; an alias adds no second effect or audit marker.

| Required attempt | Independent expected state |
| --- | --- |
| Same request key, identical full command | Return existing financial journal or nonfinancial initialization ID; one opening effect. |
| Different request key, identical full command | Return the same effect ID with permitted retry alias only; immutable policy/details/history unchanged. Zero aliases use `zero_requests`, without a normal financial request or second marker audit. |
| Same or different key, changed full content | Reject without financial mutation: include amount, date, role mapping/setup, party/stock/GRNI/cheque/advance/provenance/reference differences, not just derived journal lines. |

| Generic manual/import posting into mapped controls | Reject at command boundary even when balanced. |
| Generic linked reversal of a detailed control opening | Reject; unsupported reversal cannot orphan/erase registers. Original stays intact. |
| Locked period, wrong company, invalid policy/history or tampered backup | Reject before committed mutation; explain error and recovery. |
| Zero-opening key collides with ordinary financial request, or the reverse | Reject; never reinterpret the request key or create a second economic/initialization effect. |
