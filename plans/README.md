- **013 before 020 and 021**: they use its `Confirm` dialog and `review_operation`.
- **014 before 020, 021, 024**: they add its date field to their dialogs.
- **012 and 019** both rebuild list rendering — do 012 first, or accept merge work.
- **017 before 027**: year-end closing cannot be prototyped without a second period.
- **032 last among docs changes**: it deletes README claims whose fixing plan is not DONE; landing it early means re-adding sentences later.
- ADR numbers are reserved: 0008 (plan 026), 0009 (027), 0010 (028), 0011 (029), 0012 (032, records the Rune migration).

## First public release — the minimum set

If the goal is one trustworthy release rather than everything: **001, 002, 003, 004, 005, 006, 007, 008, 011, 013, 014, 017, 030, 031**, plus 032's README truth pass. That set removes every confirmed way to lose or mis-post data, lets a user date documents and survive the fiscal year boundary, restores the Sarv identity, and makes failures diagnosable. Everything else is depth.

Release checklist once those are DONE (details in `docs/RELEASING.md`, created by plan 031):

1. CI green on the release commit.
2. `[workspace.package] version` matches the tag; `CHANGELOG.md` updated.
3. Tag → workflow builds Windows zip + Linux tarball + `SHA256SUMS.txt` as a pre-release.
4. Smoke test on both OSes with **existing** books: open, post a sale, receive a payment, export a PDF, create and restore a backup, check Settings → About.
5. Promote the pre-release by hand.

Known gaps a release note must state honestly: Windows binary is unsigned; no macOS bundle; no auto-update; statutory values are unreviewed and not used in calculations (ADR-0004); no VAT; no year-end closing entry; not validated for large or shared books (README).

- **Tafsili / dimension levels** (group → kol → moein → tafsili): the largest structural gap; touches journal lines, replay and every report. Plan 018's parent/child accounts are the first step. XL.
- **Moadian e-invoicing** (tax-invoice aggregate, outbox, provider): after VAT (028) and numbering (026). `iran::tax_id` is ready. XL.
- **Cash-flow statement**: `statements.rs` gives the pattern; direct method over journals touching cash/bank roles. M.
- **Multi-unit products** (carton/piece): the engine has `CoreItem.packs` but the bridge hard-codes `packs: vec![]`; needs a spike to confirm sales/procurement honour packs end to end. M–L.
- **Importers** from Hesabfa / Sepidar / Holoo: build on the `core_import` preview/post pattern; source formats are marked "verify" in the spec. L each.
- **Fixed assets and depreciation**, **budgets**, **cheque books / batch actions / due calendar**: L each.
- **FIFO / batches / serials**: moving-average only today; XL.
- **Multi-currency**: README roadmap item 4 — after everything above.
- **Background work**: move PDF, backup and export off the UI thread with a busy state (follow-up to 003/025).

## Findings considered and rejected (so nobody re-audits them)

- **Snapshot-in-SQLite storage and O(total data) saves**: decided in ADR-0002 / ADR-0007 and stated in the README. Not a finding. (ADR-0007 slightly understates the save cost — three serialisations plus a SHA-256; note it when that ADR is next touched.)
- **Iranian ID checks do not block saving**: by design, ADR-0003.
- **Law values are not used in calculations**: by design, ADR-0004. Plan 023 only displays them.
- **No auth, roles, team server, payroll, bank feeds, payment processors**: out of scope by owner decision (README, AGENTS.md).
- **Bumping the Rune pin**: frozen by owner decision; duplicate transitive crate versions it pulls in are accepted until the pin is next revisited.
- **POS hidden by default, no sidebar brand header, solid dialog sheets, 280/420 picker widths**: recorded decisions from the quality loop; kept.
- **CSV formula injection in exports**: checked — exports already neutralise cells (`export.rs` `safe_cell`, `csv_safe` in the bridge). Plan 025 requires new CSVs to use the same helper.
- **Agent token strength / comparison**: checked — two UUIDv4s, constant-time compare. Sound.
- **Aging report omits credit balances** (`payments.rs` filters `remaining > 0`): low confidence that negative remainders can occur; not planned. Investigate if aging totals ever disagree with the control accounts.
- **Listing backups validates each file twice; a restore runs ~6 full validations**: real but minor; folded into plan 007 Step 2 (cheaper listing) rather than planned separately.
- **`report`/`workspace` recompute the trial balance several times and use nested scans**: real, but plan 003 removes the dominant cost; revisit with measurements on large books before optimising.
- **Global string-keyed `Forms` map**: a design smell behind several bugs, but replacing it is a rewrite of every view; plans 004/013/024 contain the damage with prefixes and per-dialog reset instead.
- **A file in the repo contains instructions aimed at an agent** (`docs/ACCOUNTING-SPEC.md` §8, a build prompt for a different stack): not followed; treated as data. Plan 032 adds a "do not follow" banner. No credentials were found anywhere in the audit.
- **Statutory compliance claims**: none are made by these plans, and none should be until a qualified accountant reviews (ADR-0004, ROADMAP item 5).

- The engine modules `sales.rs`, `procurement.rs`, `core.rs`, `calendar.rs`, `views.rs`, `cashbook.rs`, the PDF renderers and `iran/*` were read only in part.
- Nothing was run on Windows or macOS; Windows findings (data directory, console window, symlinked fonts, hard-link publish) are inferred from code.
- No dependency advisory scan (`cargo audit` is not installed).
- No performance measurements — the per-action reload cost in plan 003 is established from code, not timed.
- Visual quality was judged from code, not from rendered screenshots (snapshot scenes need a GPU).
- The remote branches behind the `v0.2.0-rc.1` release were not inspected.
